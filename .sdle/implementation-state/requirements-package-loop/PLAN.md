## 1. Cross-cutting design (applies to all releases)

### 1.1 Compatibility rule (the biggest regression risk)
`requirements/todo-api.md`, dry runs 01–22 and nearly every test bind documents that have **no ID grammar** (V). Therefore:
- Every trace/package/handoff refusal is **inert unless the WorkItem's binding contains a file under `requirements/packages/<package-id>/`**. `trace_scope(paths)` returns `None` for any other binding and every new precondition returns immediately on `None`.
- **Two behaviours are deliberately universal**, and everything else is package-scoped: (a) `review_type_mismatch` (table built from existing usage, §3.3); (b) tree-bound evidence (§3.6): a manifest built after R2 always records `treeDigest` and the gate enforces it, because the G08 hole (edit after a passing run) affects every WorkItem and scoping the fix to packages would leave it open. Evidence **without** a `treeDigest` field (built before R2) keeps the current checks and is accepted; the gate says so in its output. Regression surface = the manifest/evidence tests (`test_units_implementation_evidence.py`, `test_units_manifest_changes.py`, `test_integration_06_to_09.py`, the dry-run contracts); each is run first and any change is ledgered with its cause.
- `requirements bind --all-current` currently `rglob`s `requirements/` (V, `_cmd_requirements_bind_locked`). It would sweep package files in. Change: `--all-current` **excludes `requirements/packages/`**; regression test.

### 1.2 Engine-written record pattern (reused, not invented)
New records copy `requirements.json`: version field, `workitem`/identity field, a self-digest, atomic write via `write_atomic`, one read path that raises an `IntegrityError` (exit 3) when the file is not one the engine wrote (`read_requirements_binding` / `validated_binding`, V). Reviews use `read_reviews` / `review_status`. Evidence uses `reserve_evidence`, the engine's only exclusive-create site (V; pinned by test). Locking uses `exclusive_file_lock` / `refinement_mutex` (V).

### 1.5 Where the policy lives (L2)
**Release split (R2-007):** `unmapped_verification_blocks` (and its validation, tighten rule and old-pin fallback tests) ships in **R2** with D10; `implementation_loop_max_iterations` and its loop-specific upgrade tests ship in **R3**. The built-in policy `GOVERNANCE_POLICY_BUILTIN` (`sdle.py:4038`) gains two keys: `implementation_loop_max_iterations` (built-in 3) and `unmapped_verification_blocks` (built-in `false`). `_refuse_weakening` (`sdle.py:4428`) gets two shapes: a repository override may **lower** the iteration limit or **raise** the blocking switch only (tighten-only, per ADR-011). The policy sha already pinned at first governance record means a WorkItem keeps the values it started under. A WorkItem pinned before R3 therefore **lacks** the two new keys. Pins are never rewritten. Such WorkItems may start a loop with those defaults. Tests: built-in and overridden policies pinned before the change; reassessment preserving the pin; `loop begin` after upgrade.

## 2. Release R1 — package contract, SA approval, intake, handoff

### 2.1 Package contract (designed from the brief; owner-reviewable)
```
requirements/packages/<package-id>/
  package.json                      # manifest, engine-validated
  overview.md  traceability.md  open-issues.md       # core
  work-items/WI-001-<slug>/requirements.md           # one per package work item, with a readiness verdict
  <supporting>.md                                    # only if warranted; absent ones named in overview.md with a reason
```
`package.json`: `packageVersion`, `packageId`, `sources[] {path, sha256, statedVersion|statedDate}`, `idGrammar {prefixes: {FR, BR, AC, NFR, SEC, ...}, pattern per prefix}` (declared once), `files[] {path, role, sha256}`, `workItems[] {id, slug, readiness: READY|NOT_READY, requirementIds[], file}`, `exclusions[] {id, disposition, reason}`, `requirements[] {id, kind, statement, status, supersedes?, source{doc, anchor} | clarification{ref}, workItem|excluded}`, `openIssues[] {id, question, affects[], blocking, disposition}`.
Requirement IDs are immutable and never reused; a split/merge/move retires the ID and the replacement carries `supersedes`. The engine extracts IDs **only** by the declared grammar (never wording).
Rationale for a JSON manifest holding the machine facts beside human markdown: the engine needs structure it can validate deterministically; the SA reads markdown. `traceability.md` is generated from the manifest by the orchestrator and checked by `package validate` for agreement (every manifest ID appears; no ID appears that the manifest lacks).
Sizing: the reference SRS is ~3,100 paragraphs, with ~117 UC, ~79 ST, ~55 SR IDs. The package for it is large, so `package show` paginates by work item and the approval display (D05) shows overview + work-item files + open issues + verdicts; supporting files are listed with digests.

**Hash fields and editing.** `files[].sha256` in `package.json` makes any direct edit of a package file look like corruption. Two distinct states are therefore defined: *content changed* (`package_files_changed`, repairable) and *manifest invalid* (`package_manifest_invalid`, integrity, exit 3). `package reseal --package <id>` is the only way back from the first: it re-reads the files, recomputes `files[].sha256` and the package digest, re-validates, re-checks the traceability agreement, **keeps the approval history**, and leaves the package `stale` until re-approved. Refinement of a package file (`refinement apply`, the only permitted editor of `requirements/`, available **before `init` only**) is therefore followed by `package reseal`, then `package approve`, then `init`; AS-07 is extended to that whole sequence. After `init` the route is staging + `package import --replace` + approve + `package adopt` (§2.3).

### 2.2 Commands (`sdle.py`; registered in `build_parser` next to `requirements`, L17228)
All JSON on stdout, exit codes 0/1/2/3, stdlib only. `package` is a **repository-level** group like `config`/`architecture`: added to `RUNTIME_FREE_COMMANDS` (L2516) except `intake`, which binds a WorkItem.
| Command | Behavior |
|---|---|
| `package import --staging <dir>` | scan staging files with the untrusted-content scanner (`cmd_scan` machinery); run `package validate` logic; copy to `requirements/packages/<id>/` via the engine (the only writer); compute and record the package digest. Refuses if the target exists with a different digest unless `--replace` (which leaves any approval stale). Source documents are read, hashed and **never written** (AS-09). |
| `package validate [--staging <dir>|--package <id>]` | pure reader. Refuses (exit 1, `package_invalid`, listing **every** offender with a per-rule code): `package_id_duplicate`, `package_id_outside_grammar`, `package_reference_dangling`, `package_requirement_unsourced`, `package_source_unknown`, `package_scope_unassigned`, `package_workitem_no_criterion`, `package_ready_with_blocking_issue`, `package_core_file_missing`, `package_supporting_file_empty`, `package_traceability_disagrees`. |
| `package approve --package <id> --approver <name> --role <role> --wording <text>` | appends one record to the repository-level ledger: package id, digest, approver, role, timestamp, wording, previous-record hash. Refuses `package_invalid` if validate fails, `package_not_imported` if absent. Identity is recorded, not verified (documented boundary, same as every gate). |
| `package show [--package <id>] [--diff]` | pure reader: revision digest, approval status (`approved`, `stale`, `unapproved`), history; `--diff` against the last approved revision (for re-approval display). |
| `package reseal --package <id>` | after refinement edited a package file: recompute hashes and digest, validate, keep history, leave the package `stale` (see §2.1). Refuses `package_manifest_invalid` if the manifest itself was damaged beyond file hashes. |
| `package intake --package <id>` | per package work item: `workitem create`, `requirements bind` (the work item's `requirements.md` as primary plus the shared files it cites), `governance assess`. Reuses `cmd_workitem_create`, `_cmd_requirements_bind_locked`, `cmd_governance_assess` unchanged, idempotent (an existing intake WorkItem is reported, not recreated). Optional refinement stays the existing pre-`init` module. Because intake runs before approval it never requires one. |

### 2.3 Repository-level approval ledger
`.sdle/package-approvals/<package-id>.json`: an array of records with a hash chain (`prev`, `hash` over canonical JSON), written only by `package approve`, read by `read_package_approvals` (fail-closed, exit 3 `package_approvals_invalid` on a broken chain). Derived from `project_root` only, never the bound WorkItem (ADR-013 precedent). **Outside the package directory so an approval does not change the digest it approves** (the digest covers `requirements/packages/<id>/` only).
Added to: `Paths`; `FENCED` in `hooks.py` (today only `.sdle/architecture`); `SDLE_OWNED_PREFIXES`; `config_names` in `collect_validation_findings` (~L3827); `CONFIG_MEMBERS`/`CONFIG_REFERENCE_SITES`. **Decision recorded:** a package is *approved* iff its current digest equals the digest of the **latest** record for that package; a re-import after any change makes it `stale`; earlier records are immutable history. A re-approval displays the diff since the last approved revision.

**Immutable revisions (R1-006).** `package approve` copies the package's files into `.sdle/package-approvals/<id>/revisions/<digest>/` (content-addressed, engine-written, never edited, fenced, versioned). That makes `package show --diff` real and gives ID history something to check against. `package import --replace` and `package reseal` validate the new manifest against the **latest approved revision's** manifest: an approved ID may not disappear, change work item, or be reused for a different statement unless it is retired with `supersedes` on a replacement (`package_id_retired_without_successor`, `package_id_reused`, `package_supersedes_missing`, `package_supersedes_cycle`). Tests: an approved package replaced by a manifest that moves an approved ID without retirement; ID reuse; supersedes cycle; approval of an uncommitted package followed by replacement (the revision copy, not git, is the source).

**Package pin per WorkItem (R1-002).** `init` writes `package-binding.json` beside `requirements.json` (engine-written, same integrity pattern): package id, work-item id, package digest and ledger record hash it started under. Governance freshness only sees *bound* files, so a change to the manifest or an unbound shared file would be invisible to it; the pin covers the whole package. `package_pin_precondition` (pure reader) refuses `package_revision_changed` when the current digest differs from the pinned one. Placement rule (R2-003, the same one `cmd_gate_approve` and `cmd_skip` already follow for `governance_precondition`): it runs **before the first irreversible write** at every site that reaches `apply_advance` or an approval: `cmd_advance`, `cmd_gate_approve`, `_approve_drift`, `cmd_gate_omit`, `cmd_skip` (which appends its `skipped` audit entry before `apply_advance`), `cmd_gate_reject`/remediation entry points, and inside `apply_advance` as the backstop. The implementer enumerates every `apply_advance` caller by grep and the test asserts that a pin refusal leaves `state.json` and `audit.md` byte-identical for each. Adopting a newly approved revision is explicit: `package adopt --package <id>` (refused unless the current digest equals the latest approval) re-pins, appends an audit event and forces re-assessment through the existing requirements-change flow (`requirements-change.md` documents the order). **Executable route after `init` (R2-006):** `refinement` is refused once `state.json` exists (`refinement_post_init`, V), so refinement + `reseal` is the *pre-`init`* route only. After `init`, a changed package is produced in validated staging, `package import --replace` (engine write, §2.2), SA re-approval, `package adopt`, then re-assessment, with the WorkItem's audit history intact (no reset). Tests: recovery for an initialized WorkItem through that route.. Reassessment alone never re-pins. Tests: manifest-only change; unbound package file change; reassessment without SA re-approval stays refused.

## 3. Release R2 — trace, verification, review enforcement, evidence freshness

### 3.1 `trace check` (pure reader) and preconditions
`trace_report(paths, state)` returns, for the bound work item: in-scope requirement/criterion IDs, IDs found in spec.md and tasks.md (extracted by the manifest grammar), uncovered, unknown, untraced tasks, dispositions. `trace check` emits it as JSON, human text on stderr. Enforced as `trace_precondition` (called from `gate_precondition_hook` and `_approve_drift`) at:
- `gate_spec`: missing in-scope ID without an approved exclusion → `trace_spec_incomplete`; spec cites an ID not in the package → `trace_unknown_id`.
- `gate_tasks`: criterion with no citing task (a test task for a testable criterion) and no disposition → `trace_tasks_uncovered`; unknown ID → `trace_unknown_id`. Engineering tasks may cite obligation tags (constitution principle, architecture decision id, plan decision label). A task citing neither is **listed, not blocking** (D11).
- `gate_implement`: criterion with no disposition, or `blocked`, → `trace_verification_missing`. Also re-runs the `gate_tasks` coverage check so an omitted `gate_tasks` cannot leak (§1.6).
- Task text is parsed only for IDs by grammar and the three obligation-tag shapes; the grammar for obligation tags is declared in `package.json` too (so it exists once).
Getting Spec Kit to cite IDs: the specify and tasks invocation args gain an instruction line (SKILL.md "SpecKit Invocation"); no Spec Kit template is edited. **Real Spec Kit behavior is unverified until AS-30**.

### 3.2 Verification dispositions
`verified-mapped | suite-pass-unmapped | manual-evidence | excluded-approved | blocked`, per criterion, engine-recorded in a WorkItem record `verification.json` (new runtime member, same pattern as §1.2) by `verification record`. `verified-mapped` comes **only** from JUnit XML when the runner emits it and test names cite criterion IDs (D10); parsed by the engine from a path the manifest build recorded. Anything else = `suite-pass-unmapped`, shown separately, never "verified", non-blocking unless `unmapped_verification_blocks` is true in the pinned policy (L2).

### 3.3 Review enforcement
- New SKILL.md table `GATE_REVIEW_TYPES | gate_key | required review types | allowed actor types |`, parsed in `load_constants` into a new `Constants` field, with a `run_sync_checks` rule that every gate is covered (next to `gate_registered_*`, ~L15738).
- `review_precondition` selects records of an allowed type **and** actor type, then takes the newest current one; otherwise `review_type_mismatch` (exit 1). Existing usage (V): the integration drivers use `content-review` at most gates (`review_for_gate`, `REVIEW_TYPE`), `architecture-placement` at `gate_architecture`, `impact-analysis`, `constitution-review` once. Table plan: `gate_architecture` → `architecture-placement`; `gate_design` → `design-review`; `gate_implement` → `code-review`; `gate_security` → the security review type; `gate_spec/plan/tasks/analyze/constitution` → `content-review` OR the type the module instructs. **Every existing test and dry-run call that would newly fail is enumerated by a script before the change (listed in the ledger) and updated on purpose**; this is expected to touch `review_for_gate`'s default type usage at `gate_design`/`gate_implement`/`gate_security`.
- `artifact review --findings <json>` (id, severity blocking|advisory, location, obligation refs, disposition) stored in the review evidence file; a PASS is refused `review_findings_open` while a blocking finding is open.
- Reviewers get the source: code, design and security modules and agent files add the bound package files and the trace report to the delegation message, and findings cite obligation IDs.

### 3.4 Design consistency
`gate_design` review input adds package files, spec, plan, tasks and the approved placement; a conflict with an approved architecture decision is a blocking finding (AS-17). No new phase.

### 3.5 G04 fix (R1-003)
Reproduced (LEDGER). v1.0.6 `analyze` is strictly read-only (brief G03/G04); the rebaseline was only ever a hedge. The fix is to **remove** the unconditional `drift rebaseline --gate gate_tasks` from Phase 13 in `phase-execution.md`, for every WorkItem. Any change to tasks.md made during analyze then stays drift against the approved baseline, is caught by the next Step 0 check or the gate precondition, and goes to a human. An optional `--expect-sha` would be only a prompt-driven guard, so it is **not** added. `drift rebaseline` keeps its other callers and gains one rule: **for a package-bound WorkItem the public command is refused `rebaseline_not_permitted` at all times** (including while a loop is active); the shared internal baseline writer is reachable only through `tasks reconcile`, after its snapshot and unrelated-drift validation (§4.4). The only sanctioned post-approval change to tasks.md is then the reconcile policy (§4.4). Tests: an edit during analyze is drift; the removal leaves a clean run clean (existing happy-path suites); direct `drift rebaseline` refused on a package-bound WorkItem, with and without an active loop, and unable to clear unrelated drift or accept a non-policy tasks edit; unchanged for legacy WorkItems.

### 3.6 Evidence freshness
- **One digest projection (R1-001), used at test start, test end, resume and approval.** `treeDigest` is the git tree of the working tree via a temp index (`GIT_INDEX_FILE`, `git add -A`, `git write-tree`: untracked non-ignored files count, ignored don't) **with the paths of the actual `Exclusions` object from `implementation_exclusions(paths, state)` (`sdle.py:15071`) removed from the temp index** — that object is the single list both the manifest and the security-review evidence already use, and it is deliberately narrow: this WorkItem's `.sdle/` runtime, `.sdle/baseline.json`, `.sdle/implementation-state/`, `.sdle/architecture/`, `.specify/`, the bound WorkItem's Spec Kit feature directory, every *other* registered WorkItem's tree, and `workitems/index.md`. It is **not** `SDLE_OWNED_PREFIXES`. Engine bookkeeping (state, audit, manifest, evidence, reviews, loop record) therefore never moves the digest, and another WorkItem's writes do not either; code the bound WorkItem keeps under its own directory, `design/`, `requirements/`, `.sdle/config.json` and `.sdle/policies/` **do** move it, as they should. What the excluded paths carry is bound separately in the evidence: package digest, bound-requirements digest and the tasks.md digest (tasks.md lives in the excluded feature directory). Regressions: code under the bound WorkItem directory edited after the run; a config or policy edit after the run. Taken **before and after** the test run; unequal → `status: invalid_changed_during_run`, which `_implementation_evidence_shape` rejects at the gate (`test_evidence_stale`). Also records test command, runner, package digest, bound-requirements digest. Without git: sha256 over the manifest-listed files, with `treeDigestMethod: "listed-files"` stated in the manifest.
- `implementation_evidence_precondition` (L13595) recomputes and refuses `test_evidence_stale` with `mismatch: treeDigest`. The recorded `treeDigest` field is added to `_implementation_evidence_shape`. Evidence that **carries** `treeDigest` is always enforced (universal, §1.1); evidence that does not (built before R2) keeps today's checks and the gate output states that no tree binding was present. Tests: an unchanged implementation passes manifest build, review, advance, loop record and approval end to end (no false staleness from SDLE's own writes); a write to another WorkItem's runtime does not stale this one; pre-R2 evidence still approves and says so.
- Historical evidence is never deleted.

## 4. Release R3 — bounded implementation loop (inside `implement`)

### 4.1 Record and commands
`implementation-loop.json` beside `state.json`: `loopVersion`, `workitem`, `selfDigest`, `limit` (copied from the pinned policy at `loop begin`), `packageRevision`, `baseRef`, `iterations[] {n, step, stepState, treeDigest, evidenceId, reviewId, converge {digest_before, digest_after}, progressDigest, classification}`, `stopReason`, `next`. Engine-written; refused `loop_record_invalid` (exit 3) if not a file the engine wrote. Added to `workitem_runtime_member_names()` and the repo-config pins (§1.3).
Commands: `loop begin`, `loop step --step <implement|reconcile|manifest|review|converge|trace>`, `loop record`, `loop show`. **What the engine can and cannot guarantee (R1-005).** It guarantees *recorded sequence and accepted outputs*: each `loop step` is refused unless the previous step is recorded and carries a before/after snapshot (tasks.md digest, `treeDigest`, evidence id, review id), and is refused when its output duplicates an earlier one (the same evidence reused, a second `converge` with no `implement` step between, a convergence section number that already exists, a review of a stale tree). `manifest build`, `artifact review` and `tasks reconcile` consult the active loop step and refuse out of order. It **cannot** prevent the orchestrator from invoking Spec Kit `converge` twice outside the recorder; that is **convention only** unless a runtime hook enforces it, and ADR-017 and the docs say so. AS-21 and AS-25 test the recorder's refusals and the absence of duplicate recorded outputs and tasks, not the external invocation. `loop begin` refuses unless the WorkItem is at `implement` with `implement preflight` already run (base ref pinned).
Because the engine **never invokes Spec Kit or an agent** (pinned), the loop is a **recorder and referee**, not a driver: the orchestrator runs `implement`, `converge` and the delegated review; the engine validates each step's inputs/outputs, records them, evaluates the predicate and returns `continue` or a stop reason.

### 4.2 One completion predicate
`implementation_ready(paths, state) -> list[unmet]`, factored out of the existing `gate_implement` preconditions (evidence fresh and passed; newest review a current PASS of the required type; trace complete; no blocking finding open; last converge left tasks.md unchanged). `gate approve` (via `gate_precondition_hook`) and `loop record` both call it (AS-20). The existing refusal codes are preserved by mapping each `unmet` entry to its current code, so legacy refusals and tests are unchanged.

### 4.3 Stop reasons and classification
`ready_for_gate | limit_exhausted | no_progress | environment_blocker | ambiguity | test_expectation_change | tasks_drift | interrupted`, each recorded with the next action (§5 of the brief). The progress digest = hash of (failing test ids, open blocking finding fingerprints, uncovered IDs); appended tasks are not progress; the first repeat stops (D09). `test_expectation_change`: a test file deleted, the JUnit case set shrinks, or an ACC-tagged test removed/changed, detected from the manifest change list and JUnit sets between iterations. The model proposes the failure class (implementation defect, test defect, requirement ambiguity, environment blocker); the engine records it and a class of `ambiguity` routes to the requirements-change process.

### 4.4 `tasks reconcile` (D08) (R1-004)
Applies the mutation policy: only checkbox ticks on existing tasks (`- [ ]` to `- [X]`/`[x]`) and appended `## Phase N: Convergence` sections are accepted. **Why a direct, audited rebaseline rather than re-approval:** it is the deliberate D08 exception, not a technical necessity (re-approval *would* succeed after a fresh review, since `review_precondition` accepts a current PASS): `gate_tasks` and `gate_analyze` are human decisions about the plan, and a tick or a converge task during `implement` is not a new plan decision.
Authority and snapshot: `loop begin` stores a content-addressed copy of tasks.md in the evidence directory under this rule (R2-004): for every one of `gate_tasks`/`gate_analyze` that **has a recorded baseline**, the sha must equal it (otherwise `tasks_drift`, nothing stored); where **no baseline exists** (HOTFIX has neither gate; an omitted gate has none), the snapshot is established from the current content and an audited `tasks_snapshot_established` event records its digest and that no approval backed it. Reconcile rebaselines only gates that have a baseline. Tests: a complete package-bound HOTFIX loop; omitted task gates. `tasks reconcile` diffs the current file against the **last accepted snapshot** structurally (task lines parsed; any removed, reworded or reordered line or edited non-task text is `tasks_drift`; **the checkbox-only exception also applies to task lines inside previously accepted convergence sections** (R2-005), whose text and order stay frozen), appends an audit event naming the delta, stores the new snapshot, and rebaselines `artifact_shas` for the gates whose artifact is tasks.md through the **same write function** `drift rebaseline` uses (no new write path). It refuses when `drift_queue` holds any other gate or `compute_drift` reports drift on any other gate, so unrelated drift is never erased. `gate_architecture` is never touched. Tests: unrelated drift present is refused; append, accept, implement, tick, reconcile across two iterations; ticks plus a convergence section accepted; a reworded task is `tasks_drift`; no snapshot is stored on a drifted baseline.

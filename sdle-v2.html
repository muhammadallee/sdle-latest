Governance & oversight

AI contributes.
People decide.

  • Clear approval checkpoints

    Each gate shows the artifact in full before a person approves progression. The architecture placement gate and the final gate always require human approval.

  • Architecture is decided first

    Before anything is specified, each WorkItem decides where its capability lives, against an architecture catalog shared by the whole repository. No WorkItem can silently redraw an approved service boundary.

  • Rejections lead to corrective work

    A rejection must carry comments. The phase is re-run with that feedback and reviewed again before it can be approved.

  • Exceptions remain visible

    Skipped steps, omitted gates and acknowledgements are recorded in a tamper-evident audit log so the decision can be revisited.

  • Approved work stays as approved

    Each approval records a fingerprint of the artifact. If it changes afterwards, Agentic SDLC flags the change and asks for approval again.

Approach

Start with your
requirements.

Every artifact Agentic SDLC generates traces back to what you write, so the work starts there.

  1. Describe what to build in a requirements/ folder, or turn a large source document into a requirements package that a Solution Architect approves.
  2. Start the workflow in Claude Code, name the work item and choose which documents it is about.
  3. Agentic SDLC checks the requirements against twelve quality criteria, such as scope, acceptance criteria and open unknowns, and scores the risk. If they are blocked, it can help refine them, but every change in meaning waits for your acceptance.
  4. Approve where the work belongs in the architecture, then review and approve each generated artifact at its gate, through to the final security review.

Requirements are the one input Agentic SDLC never generates, and it treats them as data, never as instructions.

Technical architecture

How the workflow runs.
Where the evidence lives.

Agentic SDLC is a Claude Code skill wrapped around a deterministic Python engine. The model supplies judgement, the engine enforces the lifecycle, and the repository keeps the record.

Judgement and enforcement are separate

The skill and its modules decide what to generate and present. sdle.py owns every mechanical fact — the next phase, gate crossings, fingerprints, the audit chain — and refuses rather than warns.

Hooks are tripwires

Five Python hooks run on tool calls whatever the model decides. Where a hook overlaps the engine, the engine's refusal at the choke point is the guarantee.

The repository keeps the record

Each WorkItem's state, hash-chained audit log and evidence live under workitems/<id>/.sdle/, with the engine as their only writer. Policy, the baseline, the shared architecture catalog and requirements-package approvals live in .sdle/.

Stages and gates reflect Agentic SDLC v1.18: five flows over a 23-entry phase registry, with architecture placement before every specification. The engine remains the source of truth — sdle.sh flow show reports a WorkItem's flow and sdle.sh governance gates reports which of its gates need a human.

Before and around the flow

None of these is a phase or a gate, so they never change a flow's phase or gate count. Packages and refinement run only when asked; a requirements change is detected automatically when the WorkItem next tries to move forward, and what happens next is your choice.

Requirements packages

A large source document becomes a validated requirements package. Nothing is invented: unsupported details become open issues. A Solution Architect approves the package at an exact fingerprint, and each package work item becomes its own WorkItem. Work cannot start from an unapproved, changed or not-ready item.

Refining blocked requirements

When the quality assessment blocks, Agentic SDLC can help fix the documents before the workflow starts. Layout-only edits are applied automatically; every change in meaning waits for your acceptance. A failed check cannot quietly pass later on unchanged text.

Requirements that change mid-flight

If a bound document changes after work starts, the WorkItem stops at its next move and shows what changed. You choose: re-assess and carry on, redo from an earlier phase, finish and raise a new WorkItem, or reset. Work already approved stays approved; deciding what the change affects is yours.

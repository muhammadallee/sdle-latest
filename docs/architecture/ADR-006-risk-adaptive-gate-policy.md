# ADR-006 — Risk-Adaptive Gate Policy

**Status:** Accepted
**Date:** 2026-09
**Supersedes:** nothing. **Extends:** ADR-003 (governance inputs and artifact
review), ADR-004 (declarative flow model).
**Context:** contract §15, executed under the constraint §12 closes with.

---

## 1. The problem, stated as the contract states it

§15 asks for *"policy-driven gates without weakening governance"*, and its exit
criterion is that *"design/security are neither universally mandatory nor
casually skippable"*.

Those two clauses pull in opposite directions unless something narrows what
"policy-driven" is allowed to reach. §12 supplies it in one sentence, which is
quoted here because the whole design turns on it:

> Human approval remains policy-driven; review/validation is universal for
> governed artifacts.

So exactly **one** thing became conditional in this decision: whether a gate the
bound flow contains requires a **human approval**. Nothing else did.

Two shipped gaps were closed alongside it, both under-enforcement rather than
design: the built-in policy carried six hard floors where §15 mandates nine, and
one of the six sat a level *below* what §15 requires. Both are corrected. The
engine's own `governance policy` command reports the resulting values; they are
deliberately not restated here, for the reason §7 gives.

---

## 2. Decision

### 2.1 Policy decides whether a gate requires approval, and nothing else

Artifact generation, artifact registration, the artifact SHA baseline, TP-011
review and validation, the drift queue, the secrets scan, the test evidence at
the implementation gate, the implementation diff baseline, the audit hash chain,
the retry and remediation caps and the fail-safe transitions are all untouched
and all still universal.

A gate the policy does not require still has its artifact generated by the phase
before it, still has that artifact registered and reviewed, still records a
baseline SHA, and still participates in drift detection. What it does not
require is a human pressing *approve*.

### 2.2 "Not required" means omittable, not omitted

A gate the policy does not require is still a gate. It can be **approved** by a
human exactly as before — always permitted, because approving is always stricter
than the policy demands, and therefore never refused — or **omitted** through a
new `gate omit --gate <key>`, which refuses unless the effective policy says the
gate is not required for this WorkItem.

Three reasons, in order of weight:

1. **It cannot weaken anything by default.** Every existing driver and
   transcript approves every gate, so a run that approves everything behaves
   identically at every risk level. The default behaviour of the engine after
   this change is what it was before it.
2. **The floor is in the engine and the presentation is in the prompt.** The
   orchestrator may *ask* to omit and be told no. It can never omit a required
   gate, at any risk level, under any policy. This is CLAUDE.md's split
   verbatim: hooks and prompts are tripwires, the script's refusal at the choke
   point is the guarantee.
3. **Omission becomes an explicit, auditable event** rather than an absence.
   §15 requires every omitted gate to be explainable and auditable, and an
   automatic omission produces no event to explain.

The rejected alternative — auto-satisfying a not-required gate inside `advance`
— is recorded in §6.

### 2.3 Three dispositions, never conflated

ADR-004 introduced "the bound flow does not contain this phase". This decision
introduces "the policy does not require this gate". They are different facts and
the vocabulary is closed so they cannot blur:

| Disposition | Meaning |
|---|---|
| `required` | The bound flow contains the gate and the policy requires a human approval for it. |
| `omittable` | The bound flow contains it and the policy does not require an approval. |
| `not_in_flow` | The policy names it and the bound flow has no such phase, so the requirement is inert — and is *reported* as inert. |

`not_in_flow` is reported rather than dropped because an unreported inert rule is
how a policy comes to claim a guarantee nobody is enforcing. It is non-empty
today for the shortest flow under the built-in policy, so the report is testable
rather than theoretical.

Each `required` gate carries an ordered list of reasons, so "why did this gate
stop me" always has a machine-readable answer.

### 2.4 The terminal gate is always required, as a derived positional rule

The last gate before completion in the bound flow is required unconditionally,
with its own named reason. Without it a low-risk WorkItem could pass the final
gate with no human decision at all, auto-completing the workflow and
establishing the repository baseline — and §15's own lowest-risk list requires a
final human review, so that is forbidden by the contract at every level.

It is expressed as a positional rule over the bound flow rather than as a row in
the policy's "always required" list. That matters three times:

* **It names the real reason.** The final gate is required because it is the
  terminal human decision on the whole run, not because security review is
  universally mandatory — which is precisely what §15's exit criterion denies.
  Stating it as "security is always required" would state a guarantee under the
  wrong name.
* **It survives a future flow** whose terminal gate is some other key.
* **A repository override cannot remove it.** Overrides edit policy
  dictionaries, and a derived positional rule is in no dictionary, so
  monotonicity is not merely enforced for it — it is structurally unavailable.

### 2.5 The highest risk level's extra approvals are positional, and proved by test

§15's highest level asks for human approval before implementation and human
approval before completion. Both are positional claims about the bound flow, not
gate lists, so both are checked positionally: the completion half is §2.4's rule
at every level, and the pre-implementation half holds because in every declared
flow the last gate before the implementation phase is already required at that
level.

**Stated plainly, because implying otherwise would be dishonest:** under the
built-in policy the highest level's required gate set is *equal* to the level
below it. §15 says "plus", and what the highest level adds is satisfied
structurally rather than by an extra list entry. A repository that wants more may
add to the policy, monotonically.

Writing a runtime branch for a property that already holds by construction would
ship dead code, so it is asserted as a test over the cross product of every flow
and every level instead. An acknowledgement flag on the two positional gates was
considered and rejected (§6).

### 2.6 Nothing is stored

The requirement set is never written to `state.json`. It is derived at each
decision point from the bound flow, the governance record and the effective
policy. A stored table would be a second source of truth able to authorise an
omission the current policy forbids, and it would need a state field, a
migration row and a template change. Deriving costs one file read and buys §2.7
for nothing.

### 2.7 A recorded omission is re-derived, never trusted

`advance` is the choke point. When it finds a recorded omission at a gate it
re-derives whether that gate is still omittable *now* and refuses if it is not.
The stored value only says that a policy once permitted this; the question at
the choke point is whether the policy permits it today. Re-deriving closes the
hand-edited-state path and any window between the omission and the advance.

A second revalidation sits at the bound flow's final gate, because gates already
passed are never revisited: an omission taken at a low risk level must not
survive a later re-assessment that raised the level, and the moment the workflow
is declared finished is the last point at which refusing costs less than
unpicking a completed run. Both refusals are evaluated among the pure readers,
ahead of the first ledger append, so a refused command leaves `audit.md`
byte-identical.

### 2.8 Two guardrails were re-pointed rather than merely "preserved"

Drift detection and repository-staleness reporting both filtered on the decision
being an approval. Left that way they would have silently excluded an omitted
gate, and an omitted gate's artifact could then have changed after the fact with
no drift raised. Both now treat an omission as what it is: a decision that
baselined specific content. This is the most likely silent regression the change
could have carried, and it is the one §15's preserve list names first.

The completion summary's "all gates approved" field became **derived** for the
same reason. It reads `false` exactly when some gate was passed by a policy
omission, and `true` — unchanged, byte for byte — for every run that approved
everything.

### 2.9 No exception mechanism

§15's evidence clause lists "excepted" among the states that must be auditable.
This decision ships no producer for that state, deliberately. An exception path
is a way to bypass a *required* gate, which is precisely "casually skippable";
with no producer there is nothing to audit. `gate omit` therefore takes no
`--force`, `--reason` or override flag, and `skip` remains what it always was —
a failed-step recovery that is confirmed, warned and audited.

## 3. What the engine guarantees about an omission — and what it does not

This section exists because a guarantee stated without its qualifier is worse
than no guarantee.

**Guaranteed.** An omission was permitted by a deterministic policy evaluated at
the moment it was taken and re-evaluated at every later decision point; it is
recorded in `state.json` as a decision distinct from an approval; it is
explained in `audit.md` by an entry naming the gate, the policy source, the final
risk level and the fact that no human approved it; its artifact was generated,
registered, reviewed and fingerprinted exactly as an approved gate's would be;
and it could **not** have been chosen for a gate the policy required, at any risk
level, under any policy, by any caller.

**Not guaranteed.** The engine cannot tell whether a human being or the
orchestrator issued any gate command — `approve`, `reject` or `omit`. That trust
model is unchanged from every other gate and from every version of SDLE that
preceded this one: the engine records who the actor claims to be, enforces what
must be true of the content and the sequence, and refuses what the policy
forbids. It does not authenticate the operator. Nor does it judge whether the
governance record's declared risk signals are an accurate description of the
work; that remains a claim by its author, checked only for vocabulary and
internal consistency, exactly as ADR-005 says of discovery findings.

## 4. The hard floors

§15 names nine minimum floors. Four map onto a signal the policy already had;
five did not, because no existing signal's *definition entails* the condition
§15 names. The rule applied throughout was: **reuse an existing signal only when
naming that signal necessarily means the §15 condition is present.**

Five new signals were added rather than widening existing ones, in each case
because widening would have been blunt over-enforcement — flooring every
migration at a high level because *some* migrations are destructive, or every
WorkItem that touches a secret because *some* expose a credential, would make
the floor say something §15 does not say. One existing floor was raised, because
it shipped below the level §15 mandates.

Every one of these edits is a **tightening**: no weight dropped, no threshold
rose, no floor fell, no floor was removed. Weights were chosen so that each new
signal alone reaches at least its own floor by score too, which keeps the floor a
floor rather than the only thing holding the level up.

Because the policy-weakening check compares an override against the built-in, a
repository whose override *restated* the old, lower value for the raised floor is
now refused. That is correct — it is the same refusal an attempt to lower it
would get.

The policy schema did not change, so the policy version did not change. Bumping
it would have refused every existing override, which is the opposite of the
intent.

**The values themselves are not written here.** Run `governance policy` to read
them. That is not evasion: a restatement of a security-relevant default in prose
is a second source of truth that can drift from the engine's, and this
repository has a test that fails when one appears in a document — including this
one.

## 5. Consequences

**Positive.** A low-risk WorkItem is no longer forced through eight human
approvals to deliver a small change, which was the friction §15 exists to
remove. Every gate's disposition is now reportable with a reason, so "why did
this stop me" and "why did this not stop me" are both answerable from the
engine. The nine contract floors are all present and one live under-enforcement
is fixed. The record's gate lists stopped being a field nothing reads, and the
record's version field stopped being a field nothing refuses on.

**Negative, and accepted.** A repository that wants the previous behaviour must
say so, by adding the omittable gates to its policy override; the default is now
weaker *for low-risk work* than "every gate needs a human", though it is
strictly stronger than the previous default for every WorkItem whose signals
reach the raised floors. The shipped dry-run transcripts show runs that approve
all eight gates; those remain valid runs, but they are no longer the only shape a
run can take, and updating them is left to the documentation sweep that owns
them.

**Neutral.** The state schema, the migration chain, the state template and the
version string are all unchanged, so nothing a user already holds becomes
unreadable, and a workflow in flight when the engine is upgraded continues
exactly as it was — a gate it has already approved stays approved, and a gate it
has not reached is evaluated under the new policy like any other.

## 6. Alternatives considered and rejected

| Alternative | Rejected because |
|---|---|
| Auto-satisfy a not-required gate inside `advance` | It produces no event to explain, so §15's requirement that every omitted gate be explainable and auditable would be unmet; it makes one command move two phases; and it would change the traversal of every low-risk existing test, including the frozen happy path |
| Put the final gate in the policy's "always required" list instead of deriving it positionally | It states the guarantee under the wrong name — it implies security review is universally mandatory, which is what §15's exit criterion denies — and it would sit in a dictionary an override could reason about. The derived rule is unremovable by construction |
| An acknowledgement flag on the two positionally-required gates at the highest risk level | It would refuse `gate approve` for the highest-risk variants of the shipped risk differential, which drives the frozen happy path. Buying a marginal acknowledgement by editing the one test file that must stay byte-identical is the wrong trade; the property is real and is proved by test instead |
| Widen an existing broad signal to cover a narrow §15 floor | Over-broad in both cases it was considered: it would make routine work reach a level §15 reserves for a specific hazard |
| Store the derived requirement set in `state.json` | A second source of truth able to authorise an omission the current policy forbids; needs a schema field, a migration row and a template change; and it defeats the re-derivation in §2.7 |
| An exception or waiver mechanism for a required gate | §2.9 |
| Make flow membership itself risk-conditional | ADR-004 owns which phases execute, and §13 forbids conditional branching in the lifecycle. A gate requirement is a boolean derived from three inputs, not a branch |

## 7. Invariants this decision is bound by

* **One source of truth per fact.** No policy value, risk-signal identifier or
  gate-requirement table appears in any prompt or documentation file, including
  this one. The vocabulary reaches the prompt layer through `governance policy`
  and `governance gates`, and a test searches every versioned prose file —
  `docs/architecture` included — to keep it that way.
* **The core refuses; it does not warn.** Every path added here refuses.
* **Single writer.** Every new refusal is evaluated before the first ledger
  append, so a refusal leaves `audit.md` byte-identical and the hash chain
  verifiable.
* **Gate discipline.** No gate is passed without an explicit, recorded decision.
  An omission is a decision.
* **Gates stay in the parent session.** A gate needs artifact content in
  conversation for a human decision; nothing here delegates one.
